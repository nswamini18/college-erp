1. Executive Abstract, Problem Statement & Objectives

1.1 Project Abstract

The Campus ERP System is a multi-tier, enterprise-class Academic Information Management and Relational Database Management System (RDBMS) engineered to orchestrate collegiate administration, faculty scheduling, student registration, curricular turnout tracking, term examinations, library circulation, and financial accounting. Powered by MySQL 8.0 (InnoDB), a high-throughput Node.js / Express.js REST API, and an intuitive React 18 Single-Page Application (SPA), the system maintains strict relational normalization in Third Normal Form (3NF) across 50 database tables representing 1,000 enrolled students and 60 faculty members across five departments.

1.2 Problem Statement & Institutional Motivation

Academic institutions frequently grapple with fragmented record systems, disparate flat spreadsheets, and stale web caches. In legacy software:

  • Duplicate Attendance Vulnerabilities: Network re-transmissions or instructor re-saves frequently produce multiple identical session records, artificially skewing statutory attendance percentages.
  • Asynchronous State Drift: Instructor actions (such as attendance marking or timetable rescheduling) fail to propagate to student terminals in real time without manual application restarts.
  • Insecure Direct Object References (IDOR): URL tampering allows students to query unauthorized personal records by altering query parameters.
  • Resource Scheduling Clashes: Lack of cross-entity boundary checks permits instructors, student cohorts, or physical lecture halls to be double-booked at identical intervals.

1.3 Core Project Objectives

  • Third Normal Form (3NF) Relational Architecture: Design a cohesive relational schema eliminating redundancy, update anomalies, and transitive dependencies.
  • Multi-Row ACID Transaction Engine: Implement atomic attendance logging with concurrency row locking (SELECT ... FOR UPDATE) and automatic rollback.
  • Idempotent Session Upserts: Ensure repeated submissions for identical cohorts and hours update existing records rather than producing redundant rows.
  • Three-Way Conflict Engine: Detect classroom, faculty, and student schedule collisions using relational interval logic.
  • Identity Isolation & Security: Enforce JWT token identity extraction at the database query layer, rendering the system impervious to IDOR attacks.

1.4 Scope & Operational Parameters

The system models five specialized engineering disciplines: Computer Science (CS), Electronics & Telecommunication (ENTC), Information Technology (IT), Artificial Intelligence & Data Science (AIDS), and Electronics & Computer Engineering (ENCE). Exactly 1,000 active students (distributed across 20 cohort divisions: CS-1..4, ENTC-1..4, etc.) and 60 faculty instructors (12 per department) are modeled with complete historical attendance, timetable, fee, exam, and library records.

6. Normalization Analysis (1NF, 2NF, 3NF)

The relational architecture was developed through systematic normal form decomposition:

  • First Normal Form (1NF): All attributes contain atomic data. Multi-valued contacts are split into student_contact and student_address. Repeating groups of attendance or marks are strictly eliminated into relational tuples.
  • Second Normal Form (2NF): No partial dependencies exist. In junction entities like attendance_record(session_id, student_id), non-key status attributes depend strictly on both components of the composite primary key.
  • Third Normal Form (3NF): No transitive functional dependencies exist ($X \rightarrow Y$ and $Y \rightarrow Z$). For example, department metadata (HOD, location) is not duplicated inside student or faculty tables; rather, both reference department_id as an immutable foreign key.

7.3 ACID Transaction Engine & Isolation

During attendance logging, partial updates are intolerable. If an update crashes midway across a 50-student roster, the database must not be left with orphan rows. The transaction model guarantees:

  • Atomicity: BEGIN TRANSACTION wraps session upsert and all student marks. Any error triggers ROLLBACK.
  • Consistency: Relational foreign keys and composite unique keys guarantee that only existing students are recorded.
  • Isolation: Row-level locks (SELECT ... FOR UPDATE) prevent concurrent faculty updates from overwriting the same lecture hour simultaneously.
  • Durability: Write-ahead redo logging guarantees that once COMMIT returns, records survive server power loss.

8. Important SQL Queries with Execution Analysis

Query 1: Statutory Debarment Detection (HAVING Clause + Aggregate Filter)

SELECT s.roll_no, s.student_name, d.department_name, sec.section_name, sub.subject_code, COUNT(ar.record_id) AS total_conducted_sessions, SUM(CASE WHEN ar.status = 'Present' THEN 1 ELSE 0 END) AS attended_sessions, ROUND((SUM(CASE WHEN ar.status = 'Present' THEN 1 ELSE 0 END) / COUNT(ar.record_id)) * 100, 2) AS attendance_pct FROM student s JOIN department d ON s.department_id = d.department_id JOIN section sec ON s.section_id = sec.section_id JOIN attendance_record ar ON s.student_id = ar.student_id JOIN attendance_session ses ON ar.session_id = ses.session_id JOIN subject sub ON ses.subject_id = sub.subject_id GROUP BY s.student_id, s.roll_no, s.student_name, d.department_name, sec.section_name, sub.subject_id, sub.subject_code HAVING attendance_pct < 75.00 ORDER BY attendance_pct ASC;

Analysis: Demonstrates multi-table joins across five entities. Utilizes conditional aggregation (CASE WHEN) inside SUM, groups by student and subject, and utilizes HAVING to filter aggregated percentages below the statutory 75% examination threshold.

Query 2: High Academic Achievers (Correlated Subquery)

SELECT s.roll_no, s.student_name, d.department_name, ROUND(AVG(m.marks_obtained), 2) AS student_avg_marks, ( SELECT ROUND(AVG(m2.marks_obtained), 2) FROM marks m2 JOIN student s2 ON m2.student_id = s2.student_id WHERE s2.department_id = s.department_id ) AS department_overall_avg FROM student s JOIN department d ON s.department_id = d.department_id JOIN marks m ON s.student_id = m.student_id GROUP BY s.student_id, s.roll_no, s.student_name, d.department_name, s.department_id HAVING student_avg_marks > department_overall_avg ORDER BY student_avg_marks DESC;

Analysis: The correlated subquery dynamically calculates the departmental mean mark for each candidate's branch. The outer query isolates students performing strictly above their peer benchmark.

Query 3: Three-Way Timetable Conflict Engine Check

SELECT t.timetable_id, s.subject_name, sec.section_name, t.start_time, t.end_time FROM timetable t JOIN subject s ON t.subject_id = s.subject_id JOIN section sec ON t.section_id = sec.section_id WHERE t.room_no = ? AND t.day_of_week = ? AND NOT (t.end_time <= ? OR t.start_time >= ?);

Analysis: Executes boundary interval arithmetic. If any row satisfies the condition, an overlapping lecture is scheduled in that physical classroom, returning an immediate HTTP 409 Conflict error to prevent double-booking.

10. Security, Authentication & IDOR Isolation

Insecure Direct Object References (IDOR) represent one of the most pervasive flaws in academic web systems. In this architecture:

IDOR Mitigation Principle: The server never trusts client-supplied primary keys in URL parameters (e.g. /api/students/profile?student_id=6). When a request is processed, authentication middleware decodes the cryptographically signed JWT token, extracting the immutable req.user.student_id. All subsequent database queries bind strictly to this verified session token.

10.1 Password Security & Demonstration Mode

  • Passwords are hashed using Bcrypt with 10 salt rounds. Plaintext passwords are never committed, seeded, or returned in API payloads.
  • Student View Preview Mode: Faculty members can inspect any student's live academic records via /api/faculty/preview-student/:id directly inside the faculty portal. Passwords, hashes, and session secrets are completely excluded from the projection.

15. Comprehensive DBMS Viva Voce Preparation (25 Questions & Answers)

Q1: Which storage engine was chosen for MySQL in this project, and why?
Answer: MySQL's InnoDB engine was selected. Unlike MyISAM, InnoDB supports ACID transactions, row-level locking, foreign key referential integrity constraints, and write-ahead redo logging for crash recovery.
Q2: What normal form is the database schema in, and how was it achieved?
Answer: The database is in Third Normal Form (3NF). Every column contains atomic values (1NF), no non-key attribute is partially dependent on any candidate key (2NF), and all transitive dependencies ($X \rightarrow Y \rightarrow Z$) have been eliminated by extracting master entities (departments, designations, fee structures) into separate tables (3NF).
Q3: How does the system prevent duplicate attendance records when an instructor re-submits?
Answer: The database enforces a composite UNIQUE KEY uk_session_student (session_id, student_id) on attendance_record. In the backend, saveAttendance queries attendance_session with FOR UPDATE to lock the row, reuses the existing session ID, and executes INSERT ... ON DUPLICATE KEY UPDATE status = VALUES(status) within an atomic transaction.
Q4: How are ACID properties guaranteed during attendance logging?
Answer: Atomicity: Enclosed in START TRANSACTION and COMMIT; errors trigger ROLLBACK. Consistency: Foreign keys ensure only valid students are logged. Isolation: Row-level locks prevent concurrent race conditions. Durability: InnoDB write-ahead logs ensure committed data survives system crashes.
Q5: What is the purpose of database views in this system?
Answer: Views like v_student_attendance_summary encapsulate complex multi-table joins and calculations inside MySQL, improving query maintainability, performance, and preventing code duplication across frontend/backend layers.
Q6: What is an Insecure Direct Object Reference (IDOR) and how is it eliminated?
Answer: IDOR allows unauthorized access by changing parameter IDs. The system mitigates IDOR by binding queries strictly to req.user.student_id decoded from the cryptographically signed JWT token, completely ignoring client-supplied URL query parameters.
Q7: How does the timetable conflict engine detect overlapping classes?
Answer: The backend queries MySQL with interval arithmetic: NOT (end_time <= ? OR start_time >= ?) for the given section, instructor, and classroom. If any row is returned, the API rejects the request with an HTTP 409 Conflict error.
Q8: Why are composite indexes used on timetable and attendance_session?
Answer: Composite B-Tree indexes on (section_id, day_of_week, start_time) allow MySQL to locate scheduled lectures directly without performing expensive full-table scans.
Q9: What is the difference between WHERE and HAVING clauses in SQL?
Answer: WHERE filters individual tuples before aggregation. HAVING filters grouped summary rows after aggregation, such as isolating students whose attendance percentage is strictly below 75%.
Q10: What is a correlated subquery, and where is it demonstrated in this project?
Answer: A correlated subquery references columns from the outer query. It is demonstrated in Report 2 to compute the overall average marks of the specific department to which each candidate belongs.
Q11: Why are passwords hashed with Bcrypt instead of stored in plaintext?
Answer: Storing plaintext passwords exposes credentials during database breaches. Bcrypt with 10 salt rounds provides cryptographic one-way hashing with deliberate computational cost resistant to brute-force attacks.
Q12: What referential integrity actions are configured on foreign keys?
Answer: ON UPDATE CASCADE ensures primary key changes propagate to child rows. ON DELETE RESTRICT prevents accidental deletion of master entities (such as departments or instructors) that have active dependent records.
Q13: How does the Faculty Preview Mode function without exposing student passwords?
Answer: The endpoint /api/faculty/preview-student/:id queries academic tables and views for the designated student and returns profile and attendance data. The password hash is explicitly excluded from the SQL SELECT projection.
Q14: What is connection pooling in mysql2/promise?
Answer: Connection pooling maintains a pool of 10 persistent database sockets, avoiding the latency overhead of establishing a new TCP handshake and MySQL authentication on every HTTP request.
Q15: How does the system prevent SQL Injection vulnerabilities?
Answer: All database interactions utilize parameterized prepared statements (e.g. query('SELECT ... WHERE roll_no = ?', [val])), ensuring user inputs are treated strictly as data literals and never interpreted as executable SQL syntax.
Q16: What is the difference between surrogate keys and natural keys?
Answer: Natural keys (PRN, Roll Number) exist in the institutional domain. Surrogate keys (e.g. student_id INT AUTO_INCREMENT) are synthetic, immutable, and computationally optimal for joining relational tables.
Q17: What cardinality exists between student and user_account?
Answer: Exactly one-to-one (1:1), enforced by a UNIQUE foreign key constraint on user_account(student_id).
Q18: What is the difference between COUNT(*) and COUNT(column)?
Answer: COUNT(*) tallies all rows in the group, including rows with NULLs. COUNT(column) counts only rows where the specified column evaluates to a non-NULL value.
Q19: How are library overdue fines calculated in the database?
Answer: Calculated via SQL date arithmetic: GREATEST(0, DATEDIFF(CURDATE(), due_date) * 5) inside v_library_overdue_books.
Q20: What error code does MySQL return on foreign key violation?
Answer: MySQL rejects the operation with error ER_NO_REFERENCED_ROW_2 (Error 1452: Cannot add or update a child row: a foreign key constraint fails).
Q21: Why are financial fees stored as DECIMAL(10,2) instead of FLOAT?
Answer: FLOAT uses binary floating-point representation, causing inexact rounding errors. DECIMAL(10,2) is an exact fixed-point numeric type essential for monetary calculations.
Q22: How does the backend monitor database availability?
Answer: The endpoint /api/health invokes connection.ping(). If MySQL is unreachable, the frontend displays actionable connection diagnostics rather than unhandled fetch errors.
Q23: How does ON DUPLICATE KEY UPDATE operate under the hood?
Answer: If an INSERT statement violates a PRIMARY KEY or UNIQUE constraint, MySQL automatically executes an UPDATE on the existing row, preventing duplicate insertion exceptions.
Q24: What is the impact of normalization on write performance?
Answer: Normalization eliminates data redundancy. Updating an entity (such as a department name) requires modifying only a single row in one table, eliminating update anomalies and minimizing lock contention.
Q25: What is the significance of the 15/15 automated verification test suite?
Answer: It provides empirical proof that all DBMS mechanisms—authentication, data isolation, ACID rollback, conflict detection, view evaluation, and live propagation—function reliably under automated test conditions.
